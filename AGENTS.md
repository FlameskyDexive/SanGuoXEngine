## SanGuoXEngine project rules (强制)

This project is a port of the Unity 2022.3 game at `F:\jws2\client` (桃园 + 刘备/关羽/张飞/赵云 +
吕布 + 黄巾小兵) to XEngine. Plan and status: `docs/plans/`, `docs/PORT-STATUS.md`.

### 零 Lua，游戏代码纯 C#

- Runtime and editor code is 100% C# (`.NET 10` + XEngine; coroutines use XTask; engine analyzers
  apply). Never reference a Lua runtime (ToLua / NLua / MoonSharp / …).
- Never commit `.lua` files. The runtime never reads Lua tables and never reads the JSON under
  `Export/`.
- The original project's Lua battle logic is rewritten in C# to the demo's scope, not translated.
- `Assets/Scripts/Tests/NoLuaGuardTests.cs` fails the build's test run when any of the above breaks.

### Python 只在 Tools/

Python (`py -3`) is allowed only for the offline converters under `Tools/`: the AIBridge export
driver, Lua-table extraction, texture channel repacking and `wwise2ogg`. They are never shipped and
never referenced by runtime code. Their outputs are native assets plus a report.

### jws2 只读

- Read the source project; never edit anything under `F:\jws2\client\Assets` or `F:\jws2\Shaders`.
- Export runs through the project's AIBridge CLI
  (`F:\jws2\client\.aibridge\cli\AIBridgeCLI.exe code execute --file <.aibridge/code/*.csx>`). The
  exporter scripts live in `Tools/unity_export/` and are staged into jws2's `.aibridge/code/` cache
  folder at run time. The jws2 editor must be open and idle; the scene is opened without saving.
- Falling back to a Unity batch-mode exporter means adding Editor scripts to jws2 — ask the user
  first.

### 资产与提交纪律

- FBX-first: copy raw FBX/textures only; native materials, prefabs, clips, scenes and data assets
  are generated by `Assets/Editor/Sanguo/*` from the export JSON.
- Only in-scope assets are copied. Keep single files under 100 MB and the repository under 1 GB; no
  Git LFS.
- The repository is private: the assets are commercial content. Never publish them (no npm package,
  nothing public).
- One node = code + tests + Unity-vs-XEngine side-by-side screenshots under `docs/evidence/mN/`,
  then `git commit` (`[feat]sanguo port function + 简介`) and `git push` before the next node.
- Engine gaps found while porting are fixed on the engine's `main` as separate nodes, never patched
  inside this project.

## Workflow principles

- **Read before write.** Inspect scene/asset state first, then patch.
- **Dry-run edits with the `dryRun` flag** before applying; scene/asset writes accept
  `expectedBeforeHash` for optimistic concurrency.
- **Every write takes an `idempotencyKey` + `intent`** — they land in the operation journal, so
  history is queryable via `journal_query` and `trace-history`.
- **Verify live when behavior matters**: run the scene in the editor (`runtime_playmode`) and
  observe (`runtime_screenshot`, `runtime_stats`).

## Loading assets at runtime (non-Resources)

Rule: **when game code loads an asset dynamically and the asset is NOT under a `Resources/`
folder, the AssetBundle collector must be configured to cover it, and the load is verified in
the editor's simulated mode.**

- **Configure the collector** — `ProjectSettings/AssetBundles.yaml` (`AssetBundleCollectorSetting`;
  edited via Project Settings → AssetBundles / the AssetBundles window). Hierarchy: Packages →
  Groups → Collectors. Add (or extend) a collector whose `CollectPath` (relative to `Assets/`)
  covers the asset's folder, and pick its rules: `PackRule` (`PackTogether` whole folder → one
  bundle / `PackSeparately` per top-level asset / `PackByDirectory` per subfolder) and
  `AddressRule` (`ByPath` / `ByFileName` / `ByGuid` / `NoAddress`). `EnableAddressable: true`
  gives assets friendly string addresses.
- **Load through the runtime APIs, never loose file paths** — an `AssetRef<T>` field (serialized
  GUID reference) or `Runtime.AssetDatabase.Get(guid)`; in addressable packages the same asset
  also loads by its collector address. This is the one load path that works unchanged in the
  editor and in a bundle-built player.
- **Verify via editor simulation** — entering Play mode in the editor serves dynamic loads
  straight from the project's asset database (editor-simulate mode: no bundles are built), so
  run the scene (`runtime_playmode`) and exercise the load before touching a build.
- **Why the collector step is not optional**: an uncollected asset loads fine in the editor but
  is simply **absent from an AssetBundle-packaged player** — the player backend resolves only
  assets present in the package manifests. Assets under a `Resources/` folder are the exception
  (`Resources.Load` works in editor and player without collector coverage).


## Quick start (中文速览)

1. AI 客户端加载本目录的 `.mcp.json`（离线 CLI 服务器 + 可选的运行中编辑器服务器）。
2. 先调 `xengine_capabilities` 看当前可用工具；再读 `.xengine/harness/skills/` 里对应任务的 SKILL.md。
3. 改场景/资产前先 inspect，写入用 dryRun 验证；所有写操作带 `idempotencyKey` 与 `intent`，
   自动记入 `.xengine/journal/`（可追溯、可回放）。
4. 动态加载 Resources/ 目录之外的资产时：先在 `ProjectSettings/AssetBundles.yaml` 配置收集器
   （CollectPath 覆盖该资产目录），代码经 `AssetRef<T>` / `AssetDatabase.Get(guid)` 加载，并在
   编辑器 Play（模拟加载，无需出包）里验证——未配置收集器的资产编辑器里能加载，打进
   AssetBundle 包体后不存在。

## AI game pipeline

For a complete deterministic vertical slice, start with `game-init` and read the resulting
`.xengine/game.json`. Run `game-assemble` to materialize mock-first assets, the entry scene,
controller script and frame-indexed replay. Use `game-verify` to collect build/headless/capture,
logs, performance budgets, asset hashes and journal evidence. `game-package` creates a stable zip
containing the manifest, replay, generated game content and acceptance report. The live editor adds
`runtime_input`, `runtime_wait`, `runtime_assert`, `runtime_capture` and `runtime_stats` for the
same QA contract.
